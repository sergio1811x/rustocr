# rustocr — быстрый серверный OCR (русский + английский)

Современная замена Tesseract: HTTP-сервис и CLI на **Rust**, внутри — нейросети
**PP-OCRv5** (PaddleOCR) через ONNX Runtime. Никаких системных зависимостей:
модели и рантайм лежат прямо в каталоге проекта.

```
картинка/PDF → [детектор текста] → [вырезание строк] → [чтение (RU+EN)] → JSON / Excel
   (PDF        где текст             с выправлением      батчами по ширине,
   растериз.)  (нейросеть)           перспективы         уверенность 0..1
```

## Быстрый старт

```bash
cargo build --release          # нужен Rust 1.75+
./run.sh                       # поднимет HTTP-сервер на :8080
```

Для PDF нужны утилиты `pdftoppm` и `pdfinfo` (пакет poppler-utils):
`sudo apt install poppler-utils`.

В `bin/rustocr` лежит уже собранный бинарник (x86_64 Linux) — если он
запускается на твоём сервере, `cargo build` не нужен.

Открой `http://localhost:8080/` — там страница, куда можно перетащить картинку
или PDF и сразу увидеть текст и рамки вокруг строк.

### CLI

```bash
export ORT_DYLIB_PATH=$PWD/runtime/libonnxruntime.so.1.20.0
./target/release/rustocr файл.png            # текст в консоль
./target/release/rustocr файл.png --json    # полный JSON
./target/release/rustocr смета.pdf           # многостраничный PDF → текст
./target/release/rustocr смета.pdf --json    # JSON со страницами
./target/release/rustocr смета.pdf --xlsx вых.xlsx   # PDF → Excel с таблицами
./target/release/rustocr смета.pdf --dpi 300 --xlsx вых.xlsx   # точнее мелкий шрифт
./target/release/rustocr смета.pdf --jobs 4  # 4 страницы параллельно (≥4 ядра)
./target/release/rustocr смета.pdf --estimate          # иерархия сметы + валидация → stdout
./target/release/rustocr смета.pdf --estimate out.json # … в файл
./target/release/rustocr смета.pdf --pazl out.json     # DTO ПАЗЛ (LLM/правила)
```

### HTTP API

| Метод | Путь              | Что принимает                                        |
|-------|-------------------|------------------------------------------------------|
| POST  | `/ocr`            | сырые байты картинки/PDF или multipart (`file=...`) |
| POST  | `/ocr/json`       | `{"image": "<base64 или data-url>"}`                 |
| POST  | `/estimate`       | смета (картинка/PDF) → иерархический JSON + валидация |
| POST  | `/estimate/pazl`  | смета → DTO ПАЗЛ                                    |
| GET   | `/health`         | проверка живости                                     |
| GET   | `/`               | демо-страница (drag&drop, в т.ч. PDF)                |

```bash
# сырые байты
curl -s -X POST localhost:8080/ocr --data-binary @чек.png -H 'Content-Type: image/png'
# форма (как из html)
curl -s -X POST localhost:8080/ocr -F file=@чек.png
# многостраничный PDF — теми же способами, ответ: {"pages": [...], "text": "..."}
curl -s -X POST localhost:8080/ocr --data-binary @смета.pdf -H 'Content-Type: application/pdf'
```

Если сервер запущен с `RUSTOCR_API_KEY=секрет`, оба POST-эндпоинта требуют
заголовок `X-API-Key: секрет` (иначе — 401). Без переменной сервер открыт —
как раньше. `/health` всегда открыт (для мониторинга).

Ответ:

```json
{
  "text": "Первая строка\nВторая строка",
  "width": 900, "height": 640,
  "blocks": [
    {
      "text": "Первая строка",
      "confidence": 0.95,
      "lang": "ru",
      "box":  [42, 44, 564, 33],
      "quad": [42.1, 44.9, 606.0, 45.1, 606.2, 77.0, 43.0, 80.1]
    }
  ],
  "skipped_fragments": 0,
  "timing_ms": {"det": 200, "rec": 90, "total": 310}
}
```

- `confidence` — уверенность 0..1 (средняя по символам строки). Низкая = строку
  стоит перепроверить.
- `box` — `[x, y, ширина, высота]` рамки; `quad` — 8 координат углов
  (для повёрнутого текста).
- `skipped_fragments` — сколько строк не прочиталось из-за сбоя (обычно 0).
  Если > 0 — часть текста потеряна, запрос стоит повторить.
- Блоки отсортированы как читают: сверху вниз, в строке — слева направо.

## Настройки (переменные окружения)

| Переменная        | По умолчанию | Смысл                                                     |
|-------------------|--------------|-----------------------------------------------------------|
| `RUSTOCR_PORT`    | `8080`       | порт сервера                                              |
| `RUSTOCR_LANG`    | `auto`       | `auto` (обе модели), `ru` (только кириллица), `en` (только латиница) |
| `RUSTOCR_DET_MAX` | `1280`       | размер входа детектора: 960 быстрее, 1280 точнее на мелком шрифте |
| `RUSTOCR_DET_THRESH` | `0.3`     | порог бинаризации карты детектора                         |
| `RUSTOCR_DET_FLATTEN` | выкл     | `1` — выравнивать локальный фон перед детекцией для ВСЕХ страниц (медленнее и не всегда лучше — для бледных страниц лучше адаптивный `RUSTOCR_FADE_FLATTEN` ниже) |
| `RUSTOCR_DET_FLATTEN_RADIUS` | `8` | радиус бокс-блюра фона при выравнивании                   |
| `RUSTOCR_DET_FLATTEN_GAIN` | `8.0`   | усиление контраста при выравнивании                       |
| `RUSTOCR_DESKEW`   | вкл          | выравнивание крена страницы (0 = выкл; до двух проходов, квады возвращаются в исходные координаты) |
| `RUSTOCR_FADE_FLATTEN` | авто     | `0` — выкл, `1` — всегда, иначе авто: выцветший скан (нет чернил темнее 120, но есть светлее 220) выравнивается целиком |
| `RUSTOCR_CROP_PAD` | `0`          | запас в пикселях вокруг квада при вырезании строки (экспериментально: массово вредит тесным таблицам) |
| `RUSTOCR_BOX_THRESH` | `0.6`     | минимальная средняя уверенность блока                     |
| `RUSTOCR_UNCLIP`     | `1.5`     | во сколько раз расширять рамку вокруг текста              |
| `RUSTOCR_REC_CHUNK`  | `16`      | максимум строк в под-пачке распознавателя (16..=64)      |
| `RUSTOCR_PDF_DPI` | `200`        | DPI растеризации PDF (зажимается в 72..=400; старое имя `RUSTOCR_DPI` тоже работает) |
| `RUSTOCR_MAX_CONC` | по числу ядер | максимум одновременных OCR-задач (1..=64)              |
| `RUSTOCR_API_KEY`  | не задан     | если задан — POST /ocr требует заголовок `X-API-Key`     |
| `RUSTOCR_MODELS`  | `./models`   | каталог моделей                                           |
| `RUSTOCR_JOBS`    | авто         | сколько страниц PDF читать параллельно (на ≥4 ядрах)      |
| `RUSTOCR_LLM_URL` | не задан     | базовый URL OpenAI-совместимого API для LLM-парсера ПАЗЛ (напр. `https://api.openai.com/v1` или `http://localhost:11434/v1`); не задан — только правила |
| `RUSTOCR_LLM_KEY` | не задан     | API-ключ LLM (`Authorization: Bearer …`)                    |
| `RUSTOCR_LLM_MODEL` | `gpt-4o-mini` | модель LLM-парсера                                        |
| `RUSTOCR_LLM_TIMEOUT_SECS` | `120` | таймаут запроса к LLM (5..=600)                      |
| `RUSTOCR_ESTIMATE_DEBUG` | выкл | `1` — печатать классификацию строк сметного конвейера в stderr |
| `ORT_DYLIB_PATH`  | автопоиск    | путь к libonnxruntime.so                                  |

Пример: чеки и сканы только на русском — ставь `RUSTOCR_LANG=ru`, это убирает
подмену похожих букв латиницей (К→K) и ускоряет чтение.

## Что уже «допилено»

**Качество чтения**

- **Два алфавита в одном прогоне**: основной прогон кириллицей, неуверенные
  строки автоматически перечитываются латинской моделью.
- **Авто-поворот**: если страница читается плохо (средняя уверенность < 0.45),
  сервис сам пробует 90/180/270° и оставляет лучший вариант.
- **Длинные строки по частям**: если строка шире 26:1 (описания работ в
  сметах), она перечитывается по частям в полном разрешении и склеивается —
  без сжатия текста.
- **Пост-обработка под сметы**: `м3`/`м2` → `м³`/`м²` (а марка бетона `М300`
  не трогается), буквы-двойники рядом с цифрами (`б`→`6`, `З`→`3`,
  `О`→`0`), перегруппировка тысячных пробелов (`2103 955,86` →
  `2 103 955,86`) без склейки соседних ячеек таблицы.
- **Уверенность для каждой строки** — видно, чему доверять.
- **Наклонный текст**: блок вырезается с выправлением перспективы.

**Производительность**

- **Батчи с сортировкой по ширине**: строки читаются пачками, внутри пачки —
  похожие по ширине (как в PaddleOCR). Плотные таблицы (сметы, ведомости)
  не съедают память и читаются быстрее.
- **PDF от и до**: многостраничные документы читаются целиком, на ≥4-ядерных
  машинах — страницы параллельно (движок на долю ядер).
- **Параллельные запросы**: сервер обрабатывает их одновременно
  (по числу ядер, `RUSTOCR_MAX_CONC`), не блокируя друг друга.

**Надёжность**

- **Потеря текста видна**: сбой под-пачки распознавателя не молчит — ответ
  содержит `skipped_fragments`, полный сбой возвращает ошибку, а не пустой
  текст. На 76 страницах реальных смет — 0 потерянных фрагментов.
- **Параллельные PDF-загрузки не сталкиваются**: у каждого запроса своя
  уникальная временная папка, уборка гарантирована при любом исходе.
- **PDF не съест память**: число страниц проверяется по `pdfinfo` до рендера
  (лимит 200), растеризация идёт порциями по 8 страниц, DPI зажат в 72..=400,
  слишком большая страница (>120 Мп) отвергается с понятной ошибкой,
  растеризация ограничена по времени (600 с).
- **Защита от «декомпрессионной бомбы»**: маленький PNG, распаковывающийся
  в гигапиксель, отвергается лимитами декодирования (до 512 МБ / 20000×20000).
- **Опциональная аутентификация**: `RUSTOCR_API_KEY` + заголовок `X-API-Key` —
  для выставления сервера в интернет.
- **Ошибки записи Excel не глотаются**: неполный XLSX — это явная ошибка.

**Таблицы**

- **PDF → Excel**: табличные страницы раскладываются по колонкам геометрически
  (просветы между колонками ищутся в самой картинке, линии сетки не мешают),
  склеенные ячейки режутся и перечитываются по кускам. Нетаблицные страницы
  выгружаются колонкой текста.

**Сметный конвейер** (`--estimate`, `POST /estimate`)

- **Восстановление структуры таблиц** («аналог SLANet», детерминированный):
  полная сетка «строка × столбец» с объединёнными ячейками (colspan),
  пометкой настоящих табличных строк и перечтением разрезанных ячеек —
  `src/estimate/structure.rs`. Интерфейс `PageTable` совместим с выходом
  SLANet-класса нейросетей: геометрический путь проверен на 17 119 числах,
  нейросетевой можно подключить позже за тем же интерфейсом.
- **Иерархия сметы**: раздел → подраздел → позиция → ресурсы + шапка
  (объект/заказчик/подрядчик/номер) + итоги (по разделам, НДС, всего).
  Локальный семантический парсер без нейросетей: классифицирует строки
  (раздел/позиция/ресурс/итог), понимает шифры ГЭСН/ФЕР/ТЕР, коды ресурсов
  (1.1-1-2345, 101-0797, машины), единицы измерения (м³, м², маш.-ч…),
  роли колонок из шапки, списочные сметы «наименование | цена», итоги
  с суммой в отдельной строке, голые заголовки разделов («Кладка»),
  номера разделов не склеивает с суммами («Итого по разделу 1 6 172,50» →
  6172.50).
- **Валидация**: количество × цена = сумма по позициям; итоги разделов =
  Σ позиций; итог сметы = Σ разделов; НДС и «Всего с НДС»; дыры и повторы
  в нумерации; неразобранные строки видны в отчёте с примерами.
- **DTO ПАЗЛ** (`--pazl`, `POST /estimate/pazl`): обменный формат
  `pazl.estimate.v1` (шапка, разделы, позиции с труд/машины/материалы,
  ресурсы). Правила — всегда; LLM-парсер — опционально
  (OpenAI-совместимый API через `RUSTOCR_LLM_URL`, строгая схема ответа,
  проверка и откат на правила при любой ошибке).
- **Регрессия**: `bench/test_estimate.py` гоняет корпус реальных смет
  через `--estimate` и сверяет стабильную статистику с золотыми снимками
  `tests/estimate/golden/` (число разделов/позиций/ресурсов, итоги,
  виды ошибок валидации).

История самых сложных документов. Каркасный КД-1: 91.2% → 96.8%
(вход детектора 1280, `RUSTOCR_DET_MAX`) → 99.3% — ещё 100+ «потерянных»
чисел вернула правка «З→3 через дефис»: OCR читал «1-Зсорт» вместо
«1-3сорт» (кириллическая З неотличима от тройки на мелком шрифте) в
характеристиках пиломатериалов. РувитСтрой: 97.6% → 99.7% — целый
столбец нулей в таблице читался буквой «о» (одиночный символ без
контекста модель путает с нулём — теперь правим). СтройЕдм 191 м²:
сверхплотная таблица с очень мелким шрифтом, 87.5% → 98.9% после
честной метрики (запятая против точки). «Новый сруб»: часть чисел
«Итого по разделу» напечатана в самом PDF бледно-серым по серой
заливке (контраст ~5%) — детектор их не видит; с включённым
`RUSTOCR_DET_FLATTEN=1 RUSTOCR_DET_MAX=1664` документ поднимается
до 99.6%, но на плотных таблицах высокое разрешение детектора
фрагментирует блоки, поэтому по умолчанию — 1280 без выравнивания.
Скорость: ~7 с на страницу в среднем (2 ядра, детектор 1280,
~240 блоков на странице; 92% времени — стадия чтения).

Разбор ошибок — не «в среднем», а по типам и страницам:
`bench/analyze_errors.py` (замена цифры / потеря разделителя / склейка /
потерянная ячейка, с контекстом строки эталона).

Синтетика для регрессии: смета из 20 плотных страниц (44 позиции на страницу,
940 контрольных чисел) — все 940 чисел совпали цифра в цифру и в JSON,
и в Excel-колонках.

### Стресс-тест «плохие сканы» (8 страниц реальных смет, 1330 чисел)

| Деградация                        | Было   | Стало  |
|-----------------------------------|--------|--------|
| фото на столе (тень)              | 98.4%  | 98.4%  |
| низкое разрешение (~120 dpi)      | 98.0%  | 98.0%  |
| фото телефона (шум + JPEG q=50)   | 97.7%  | 97.7%  |
| не в фокусе (блюр 1.5 px)         | 97.1%  | 97.1%  |
| **крен 1.8° (лист криво лёг)**    | **80.8%** | **97.6%** |
| **выцветшая печать (контраст 21%)** | **85.9%** | **99.1%** |

Крен и выцветание — две самые частые беды реальных сканов — теперь
выравниваются автоматически (без потери скорости на «хороших» страницах):
`RUSTOCR_DESKEW` оценивает угол по линейным боксам детекции (взвешенная
медиана, до двух проходов — на бледных страницах первый угол недооценён),
`RUSTOCR_FADE_FLATTEN` в авто-режиме выравнивает фон страницы, если
тёмных чернил нет вовсе (пиксели <120), а светлые есть (<220)

## Честные ограничения

- **Рукописный текст** не читает (это OCR для печатного текста).
- Авто-поворот — эвристика: если картинка изначально читается уверенно,
  поворот не проверяется.
- Омоглифы: в авто-режиме редкие пары вроде латинской `O` вместо русской `О`
  возможны (визуально неотличимы). Для чисто русских документов решается
  `RUSTOCR_LANG=ru`.
- Бледный текст: в отдельных PDF числа «Итого» напечатаны бледно-серым
  по серой заливке (контраст ~5%) — детектор их пропускает, хотя
  распознаватель при наличии кропа читает идеально. Лечится
  `RUSTOCR_DET_FLATTEN=1` (+ `RUSTOCR_DET_MAX=1664`), ценой ~10%
  скорости; для обычных документов выравнивание не нужно и выключено.
  Целиком выцветшие сканы ловит адаптивный `RUSTOCR_FADE_FLATTEN` —
  он включается только когда тёмных чернил на странице нет вообще.
- На сверхплотных таблицах с мелким шрифтом (СтройЕдм 191 м², «Новый сруб»)
  часть чисел теряется или путается в последней десятой доле процента —
  в основном это замены цифр на мелком шрифте (3↔0, 1↔6) и потерянные
  десятичные запятые; видно по низкой уверенности блока.
- Восстановление таблиц — геометрический алгоритм (просветы + перечтение
  разрезанных ячеек): объединённые ячейки по вертикали (rowspan),
  вложенные таблицы и многоуровневые шапки не поддерживаются.
- Семантический парсер — эвристики по словарям и контексту: экзотические
  форматы смет разбираются частично (неразобранные строки видны
  в `unparsed_lines` и отчёте валидации — это сырьё для LLM-парсера).
- Пост-обработка чисел — эвристики; странные склейки вида
  «230518,62 0009» сознательно не перегруппировываются.

## Скорость

Замеры на 2 ядрах (в песочнице), детектор 1280; `RUSTOCR_DET_MAX=960`
ускоряет страницу примерно в полтора раза ценой точности на мелком шрифте.
На обычном сервере в 2–4 раза быстрее:

| Картинка                        | Время  |
|---------------------------------|--------|
| фото/скрин 900×640, 5 строк     | ~0.5 с |
| страница сметы A4, ~60 блоков   | ~3 с   |
| страница сметы A4, ~250 блоков  | ~7 с   |
| сверхплотная страница, ~450 блоков | ~13 с |
| PDF-смета целиком (5 страниц)   | ~25–60 с |

Для сравнения, Tesseract на ту же A4-страницу тратит ~2–3 с, при этом
ошибается заметно больше (по публичным бенчмаркам CER 0.33 против 0.20).

Опробовано и отвергнуто: динамическая INT8-квантизация rec-моделей
(`bench/quantize_int8.py` — протокол эксперимента) — на 2-ядерном CPU
в 2 раза МЕДЛЕННЕЕ float32 и точность ниже: модель почти целиком
конволюционная, dynamic quantization трогает только MatMul/LSTM.

## Идеи развития

- Серверные (не mobile) модели детектора/распознавателя: +1–2% точности,
  ×2 медленнее.
- Классификатор ориентации строк (180°) — крошечная модель.
- `PP-OCRv5 server rec` + дообучение на своих документах — максимальная точность.
- Нейросетевое восстановление структуры таблиц (SLANet-ONNX за интерфейсом
  `PageTable`) — для таблиц без устойчивых просветов между колонками;
  сейчас работает детерминированный геометрический путь.
- LLM-парсер ПАЗЛ на дообученной модели со строгой схемой — точнее правил
  на шумных сканах (интерфейс уже есть, меняется только промпт/модель).
- GPU (CUDA/TensorRT): в `Cargo.toml` у `ort` есть соответствующие feature.

Примечание: PP-OCRv6 (вышла в 2026) покрывает 50 языков, но все латиница/CJK —
русского в ней нет, поэтому для RU+EN остаёмся на паре «кириллица + латиница».
